# Work done: ultra-pro-max-finder

Branch: `chore/modernize` (local, not pushed). Date: 2026-11-01.

## What was there

An Electron app of 16 JavaScript files (about 2,400 lines) and 6 HTML pages, no tests, a one-line README ("Profinder like Linkedin automation tool"), 11 declared dependencies (more than half unused), and a lock file with 392 packages. It signs in to LinkedIn accounts, reads the ProFinder request list, writes it to a Google Sheet, and answers each request in a Playwright browser. Also tracked: `credentials.json`, `test.js` (`console.log(data)`, which throws) and `chromeMiscs.js` (never loaded; runs a download on import and needs three packages that were not dependencies).

## Credentials: the most important part of this report

- **`credentials.json` is a Google Cloud service-account key** (it has a `private_key`, `private_key_id` and `client_email`; its contents were not read or printed). It was committed to git and read from the source folder at run time. **One commit in the history added the private key; it is still there.** Whoever can read this repository can act as that service account, with access to every Google Sheet shared with it.
  - Now: untracked (`git rm --cached`; the file is still on your disk), ignored, and no longer read from the project. The app reads `GOOGLE_APPLICATION_CREDENTIALS` or `google-credentials.json` in its data folder.
  - **Rotate it:** in Google Cloud, delete that key (IAM > Service accounts > Keys), create a new one, and keep the new one outside the repository. Removing the old key from history means rewriting it and force-pushing, a push you must do yourself.
- **It was also inside every packaged build.** `electron-packager` copies the project _folder_, not the files git tracks, so the ignored-but-present key went into `app.asar` (found by listing the bundle). The package script now whitelists what to include.
- `output.xlsx` (an export of leads) was committed and removed again in the history (2 commits). I did not open it; it probably holds client names and LinkedIn profile links.
- LinkedIn **passwords were stored in plain text** (`pass.json` in the data folder). Now encrypted (see below).
- A scan of the working tree for private keys, service-account JSON, OpenAI and Google API keys finds nothing; the history has the one private-key commit above and no other key-shaped strings.

## Verification (actual runs)

- `npm test`: **262 passed**, 97.2% of lines of `src/main`; `npm run lint` and `npm run format:check` clean; `npm audit --omit=dev`: 0 vulnerabilities.
- **Mutation checks** (the defect put back, the suite must fail), 30, all caught: the first-account's-password bug, accounts wiped on add, plain-text vault, legacy file kept, no `default` fallback, `$&` in a name, any sheet link accepted, slashes in account names, 0-minute interval, overlapping runs, end date excluded, unquoted tab names, header written every time, 0-based month, one-word name cut, inverted decline logic, form opened before the template check, non-Secure SameSite=None, empty message sent, password pasted into a script, credentials filled on any site, sign-in saved twice, every header (cookies included) copied, unsandboxed request window, parallel runs, any local file trusted by IPC, schedule not started until restart, session kept after removal, no minimum window size. One early mutant (serialising sign-in checks) was equivalent, which led to simpler code.
- **End to end, the real app** (headless): the old data folder's accounts are listed; the window's real web preferences are sandbox + isolation + no Node and the page has no `require`, `process` or `ipcRenderer`; a template titled `<img src=x onerror=...>` is shown as text with no element created and no script run; a template and a sheet link can be saved (a non-Sheets link is refused with a clear message); a schedule can be set from its dialog (an invalid interval is refused in the dialog) and then shows on the account and in `schedules.json`; no console errors or CSP violations. Passed twice in a row.
- **Packaging:** `npm run package` builds and the binary starts and stays up. Listing `app.asar` found the credentials file in the bundle, which led to the whitelist; after the fix the root holds only `LICENSE`, `node_modules`, `package.json` and `src`.
- Two real bugs the tests found in my own code and fixed: bad input threw synchronously instead of rejecting; two navigation events could save an account twice. And the e2e run showed the dialog needed a minimum size.
- **Not verified:** anything against live LinkedIn or a live Google Sheet; encryption with a real keyring; Windows and macOS builds; a GitHub Actions run. See VERSIONS.md.

## Needs your attention

- **Rotate the Google service-account key** (first section), re-share your sheet with the new account, and put the new key at `GOOGLE_APPLICATION_CREDENTIALS` or `google-credentials.json` in the data folder. Without a key the app starts and everything works except the Google Sheet.
- **LinkedIn passwords:** on a machine where the system cannot encrypt, the app does not keep the password, so a session that expires means signing in again by hand. On first start with encryption available, the old `pass.json` is converted and deleted.
- **Run `npx playwright install chromium`** once (as before); the answering browser is visible, as before.
- The data folder is still `profinder` on purpose. Renaming the package would have made the app start empty.
- Behaviour you may notice: the schedule runs at its start time and then after a random 1 to 1440 minutes (not at cron-aligned minutes), the end date is included, the follow-up message is sent only when one is saved, and a request with no matching template is skipped.
- **LinkedIn's terms:** the app automates actions on LinkedIn; see the note in the README.
- The parser relies on LinkedIn's undocumented JSON; if LinkedIn changes it, rows will be skipped (and logged) rather than the whole batch failing, and the tests will not notice because their data is made up.
- Nothing pushed. To publish: `git push -u origin chore/modernize`
